# Шаблони за проектиране. Прокси

## 1. Основна идея

**Проксито** е структурен дизайн патърн, който предоставя заместител на друг обект с цел **контрол на достъпа до него**.

Когато даден обект е скъп за създаване, намира се на отдалечен сървър, изисква строги права за достъп или съдържа тежки ресурси, прякото му използване от клиентския код може да бъде неефективно или рисково.

Нека разгледаме класа `SortedArray`, който поддържа елементите си винаги в сортиран ред:

```cpp
class SortedArray {
public:
    int& operator[](size_t index) {
        // Опасност: ако клиентът промени върнатата референтна стойност
        // без да пренареди масива, нарушаваме инварианта на обекта
    }
    
    void add(int value) {
        // Добавя елемента и го поставя на правилното му място, за да запази подредбата
    }

private:
    std::vector<int> data;
};
```

Ако върнем директна референция (`int&`) чрез оператора за индексиране, клиентът може свободно да промени стойността на даден елемент (напр. да замени най-голямото число с най-малкото), без масивът да разбере и да се пресортира. Така губим контрол върху целостта на данните. Прокси патърнът решава този проблем, като връща специален обект-заместител вместо обикновена референция.

## 2. Защита, отложен достъп и видове

Освен самото пренасочване на заявките към оригиналния обект, прокси слоят капсулира и междинна логика за контрол. Това гарантира пълна прозрачност за клиентския код, който работи по един и същ начин, без да знае дали взаимодейства с реалния обект или със заместителя му, като същевременно позволява прецизно управление на жизнения цикъл и системните ресурси.

В зависимост от конкретната архитектурна задача, прокси патърнът се реализира в четири основни разновидности:

- **Виртуално прокси:** Прилага отложено зареждане (*lazy loading*), като инстанцира тежкия обект едва при първото изрично заявяване на услуга от него.
- **Защитно прокси:** Извършва автентикация и проверка на потребителските права, преди да разреши изпълнението на заявката.
- **Отдалечено прокси:** Управлява мрежовия транспорт, сериализацията и десериализацията на данните при комуникация с обект, разположен в друго адресно пространство или машина.
- **Интелигентно прокси:** Изпълнява допълнителни служебни задачи около достъпа (напр. кеширане на изчислени резултати, водене на одиторски логове или автоматично броене на активни референции).

Следният пример демонстрира как прокси патърнът се използва при оператора за индексиране на `SortedArray`, за да хване момента на промяна на стойност и автоматично да пресортира масива, запазвайки наредбата:

```cpp
class SortedArray {
public:
    void add(int value) {
        data.push_back(value);
        sort();
    }

    class ElementProxy {
    public:
        ElementProxy(SortedArray& owner, size_t index)
            : owner(owner), index(index) {
        }

        ElementProxy& operator=(int value) {
            owner.data[index] = value;
            owner.sort();

            return *this;
        }

        operator int() const {
            return owner.data[index];
        }

    private:
        SortedArray& owner;
        size_t index;
    };

    ElementProxy operator[](size_t index) {
        return ElementProxy(*this, index);
    }

    void print() const {
        for (int value : data) {
            std::cout << value << " ";
        }

        std::cout << "\n";
    }

private:
    void sort() {
        std::sort(data.begin(), data.end());
    }

    std::vector<int> data;
};
```

## 3. Предимства

### 3.1. Контрол зад кулисите

Когато клиентът напише `arr[1] = 40`, отстрани изглежда сякаш работи с обикновен масив и присвоява стойност на променлива.

Клиентският код **не подозира** и не се интересува от факта, че зад кулисите се намесва `ElementProxy::operator=`. Проксито улавя момента на промяната, записва новата стойност в `std::vector` и автоматично извиква вътрешния метод `sort()`, за да възстанови наредбата. Клиентът получава желания резултат, без да се налага сам да управлява процеса на пресортиране.

### 3.2. Принцип за отвореност/затвореност

Класът `SortedArray` и клиентският код са напълно изолирани от начина, по който се управлява достъпът до елементите.

Ако утре пожелаем да добавим нова функционалност, напр. **одиторски лог** (да се записва в конзолата кога и коя стойност е променена) или **проверка за валидност** (дали новата стойност е в позволен диапазон) - можем да го направим, като изменим единствено логиката в `ElementProxy`. Самият клас `SortedArray` остава напълно непроменен (затворен за модификация, но отворен за разширение чрез прокси слоя).

### 3.3. Подобрена сигурност

Предотвратява се възможността клиентският код да "счупи" вътрешния инвариант на структурата от данни (нейната подредба).

Ако бяхме върнали обикновена референция (`int&`), клиентът можеше свободно да промени най-малкия елемент с най-големия, при което масивът щеше да остане несортиран и да загуби основното си предназначение. Чрез проксито гарантираме **сигурност на състоянието** - масивът физически не може да бъде оставен в невалиден или нарушен вид, защото всяка модификация задължително минава през контролната точка на прокси обектa.

## 4. Недостатъци и ограничения

### 4.1. Усложняване на кода

Вместо стандартния, елементарен начин за достъп, при който `operator[]` просто връща една референция (`int&`), ние трябва да дефинираме цял отделен вътрешен клас (`ElementProxy`), да имплементираме специални оператори за преобразуване (`operator int`) и присвояване (`operator=`), както и да пазим референция обратно към масива.

За една обикновена структура от данни кодът става значително по-обемист и труден за четене. Всеки нов колега (или самите вие след време), поглеждайки към този код, ще трябва да анализира защо `operator[]` не връща директна референция и как точно се преплитат животите на проксито и масива. Това увеличава когнитивния товар и сложността на поддръжката.

### 4.2. Латентност и влошена производителност

Във вътрешността на проксито записахме автоматично пресортиране (`owner.sort()`) при всяко присвояване.

Представете си, че клиентският код реши да промени стойностите на няколко елемента подред в обикновен цикъл (напр. при масова корекция на данни):

```cpp
for (size_t i = 0; i < 100; ++i) {
    arr[i] = newValues[i];
}
```

Тъй като проксито не знае кога цикълът свършва, то ще принуди масива да се пресортира **100 пъти последователно**. Това превръща една иначе бърза операция в сериозен производителен *bottleneck*, водещ до забележима латентност, докато при директния достъп бихме могли да променим елементите на спокойствие и да сортираме веднъж накрая.
